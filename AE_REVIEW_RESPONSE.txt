1. Linux PyTorch installation and disk requirement
---------------------------------------------------

Reviewer concern
~~~~~~~~~~~~~~~~
On Ubuntu 25.10 with Python 3.13.7, the original installation occupied 5.2 GB.
Although the artifact defaults to EMBEDDING_DEVICE=cpu, the unqualified
torch==2.12.0 package from PyPI installed the complete Linux CUDA dependency
stack. The documented 5 GB free-disk requirement was therefore smaller than
the installed virtual environment alone.

Author response
~~~~~~~~~~~~~~~
Our reference deployment runs the ANCHOR client separately from the vLLM model
server, and we had provisioned the two environments independently. As a result,
our original client-side disk estimate reflected the CPU-only ANCHOR environment
we used, while the distributed installer allowed pip to resolve the generic
Linux torch wheel. On a clean Linux host, that wheel also brings in the CUDA,
cuDNN, cuBLAS, NCCL, and Triton packages even when EMBEDDING_DEVICE=cpu. We
confirm that this made the original 5 GB statement incorrect for the install
path observed by the reviewer.

We reproduced both configurations in a clean Ubuntu 25.10 x86-64 container with
Python 3.13.7. With CPU-only PyTorch, the virtual environment was 1,474,273,436
bytes, the retained pip download cache was 350,888,245 bytes, and the
all-MiniLM-L6-v2 cache was 91,635,712 bytes. Including the package itself, the
measured retained footprint was approximately 1.92 GB. With the generic
CUDA-enabled Linux PyTorch installation described by the reviewer, the virtual
environment was 5,517,943,403 bytes and the retained pip cache was
2,890,711,459 bytes. Including the package and embedding cache, that
configuration occupied approximately 8.51 GB. Both configurations completed
the deterministic smoke test successfully.

We therefore changed the installer so that it no longer installs the full CUDA
stack unconditionally. The default evaluation path explicitly installs
torch==2.12.0+cpu from PyTorch's official CPU wheel index and verifies that no
nvidia-* packages are present. Reviewers who only need the documented CPU
evaluation path can continue to use ./install.sh with 5 GB free disk. Users who
intentionally want CUDA-backed client embeddings can instead run
ANCHOR_TORCH_VARIANT=cuda ./install.sh, allow at least 10 GB free disk, and then
set EMBEDDING_DEVICE=cuda. The installer validates the selected variant in both
cases. We documented this distinction and the measured footprints in README.md,
README.txt, HARDWARE_REQUIREMENTS.md, and infrastructure/resources. The optional
CUDA client remains separate from the reference vLLM server, whose documented
disk requirement remains 100 GB.

3. Claim 3 depended on the configured LLM provider
---------------------------------------------------

Reviewer concern
~~~~~~~~~~~~~~~~
Claim 3 is documented as requiring no LLM endpoint or credentials, but its
smoke test runs main.py --graph. Graph construction eagerly called get_llm()
from four mapper factories. Consequently, an artifact/.env containing
LLM_PROVIDER=openai without an API key caused Claim 3 to fail during client
construction even though the check never contacts an endpoint.

Author response
~~~~~~~~~~~~~~~
We confirm the issue. We changed the mapper factories to construct and cache
their LLM agents lazily, when the corresponding node first executes, rather
than while the graph topology is being built. Graph rendering now constructs
the complete pipeline without resolving a provider, reading credentials, or
creating an LLM client. Normal pipeline execution still creates one agent per
compiled mapper node on first use and then reuses it.

We added a regression check to artifact/scripts/smoke_test.sh that replaces
get_llm() with a function that raises immediately and then calls build_graph([]).
Claim 3 fails if graph construction ever attempts to initialize an LLM again.
The expected Claim 3 output now records this check explicitly.

5. SHACL coverage in the packaged schemas
------------------------------------------

Reviewer concern
~~~~~~~~~~~~~~~~
The packaged UCO ontology contains SHACL definitions, but the packaged STIX
and MALOnt ontologies do not. Nevertheless, the original documentation called
all three packages "OWL/SHACL schemas," and the correction stage reported that
all STIX and MALOnt entities had passed SHACL validation. Those two Claim 2
runs therefore could not exercise SHACL constraints as the wording implied.

Author response
~~~~~~~~~~~~~~~
We confirm the distinction. SHACL is not inherently specific to UCO, but among
the three ontology sources packaged with this artifact, UCO supplies SHACL
shapes while STIX and MALOnt are OWL-only. We did not invent new constraints
for the two source ontologies. Claim 1's UCO run exercises the SHACL-capable
path; Claim 2 tests that the same extraction and mapping executable can switch
among the three ontology packages.

We changed validate_entity to distinguish three outcomes: applicable SHACL
constraints passed, the schema has SHACL shapes but none applies to the mapped
class, and the selected schema supplies no SHACL shapes. The pipeline now
reports the last case as

  [shacl_correction] skipped: selected ontology contains no SHACL shapes

instead of counting every entity as having passed. We also made the schema
scope explicit throughout the documentation and added a deterministic
preflight assertion that UCO contains shapes and the packaged STIX and MALOnt
sources contain none.

7. Functional output checks did not distinguish mapping failure from fallback
-----------------------------------------------------------------------------

Reviewer concern
~~~~~~~~~~~~~~~~
The original check_output.py verified only the output's basic JSON structure.
If every mapper agent timed out, raised an exception, or failed to make its
final tool call, mapper.py would still emit owl:Thing, rdfs:label, or
rdfs:seeAlso defaults. Such an all-fallback graph could therefore pass even
though no mapping operation had completed. The exported result also contained
no provider, model, timeout, or fallback information with which a reviewer
could distinguish a healthy run from a degraded one.

Author response
~~~~~~~~~~~~~~~
The three generic terms are intentional parts of ANCHOR's design. A mapper may
legitimately complete ontology discovery and select owl:Thing, rdfs:label, or
rdfs:seeAlso when the selected schema has no more specific suitable term. We
therefore do not treat every occurrence of a generic term as an error. The
actual defect was that the output lost the provenance needed to distinguish
that semantic decision from a value injected after an operational failure.

We now record one completion result for every entity and property mapping. A
generic URI returned through the mapper's required final tool call is recorded
as a semantic fallback and remains valid. A timeout, exception, missing final
tool call, or missing entity URI is recorded as an operational fallback. The
exported JSON includes the provider and model, aggregate and per-phase item
counts, semantic-fallback count, operational-fallback count, and the individual
operational-failure counts.

The Functional validator now checks that entity classes and property URIs are
declared by the selected packaged ontology or are one of the documented generic
terms. It requires at least one entity, one triplet, one ontology-specific
class, and one ontology-specific property. It also verifies the diagnostic
counts against the emitted graph and rejects every operational fallback. Thus,
an intentional partial fallback remains acceptable, while a run in which the
agent never completes its mapping calls can no longer pass.

8. Claims 1 and 2 were not executed by the reviewer
----------------------------------------------------

Reviewer note
~~~~~~~~~~~~~
The reviewer did not execute Claims 1 and 2 because the SPHERE host had neither
paid API access nor the accelerator capacity needed to self-host the reference
model. The chairs had asked reviewers not to purchase API access.

Author response
~~~~~~~~~~~~~~~
We understand this limitation. Claims 1 and 2 exercise ANCHOR's LLM-driven
extraction and multi-step ontology-mapping path, so they necessarily require
access to a tool-calling LLM. This can be either a hosted API endpoint, which
does not require a GPU on the ANCHOR client, or a separately hosted local model,
which requires suitable accelerator resources. The two are alternative
execution paths; reviewers do not need both.

Claim 3 is intentionally the model-free path and verifies installation, package
completeness, source and ontology parsing, dataset alignment, and graph
construction without an endpoint or credentials. It cannot replace Claims 1
and 2, which specifically cover the end-to-end LLM-dependent functionality.
Accordingly, we do not interpret the reviewer's inability to run those two
claims as a software failure, and we make no assertion that the reviewer
independently executed them.

No code change was required for this note. The LLM requirement and the two
alternative execution configurations are documented in README.md,
HARDWARE_REQUIREMENTS.md, infrastructure/access, and infrastructure/resources.
